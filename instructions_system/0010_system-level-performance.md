title: system-level-performance
trigger: when a change affects latency, throughput, or resource use across a path spanning multiple components, or when adding a data path that will be read more often than its source changes

State an explicit expected latency or cost for an operation before implementing it, based on what the operation actually does — a network round-trip, a full-table scan, an in-memory lookup, and a disk read carry different inherent costs, and the expectation should be set from that reasoning, not from hope. After implementation, measure the operation against that stated expectation; treat any result slower than expected as a bug to investigate, not an assumption to accept silently. Essentially all interactive operations should be near-instant except in the few, specific cases where slowness is an understood, inherent cost of the operation itself — a case where slowness is expected should be named as such explicitly, not left to be inferred after the fact.

This is a "measure, don't guess" discipline, not an injunction against ever measuring or optimizing: Knuth's own full statement on this — "we should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%" (*Structured Programming with go to Statements*, 1974) — is frequently quoted only in its first half, which inverts its actual meaning. The claim is to identify what matters, using measurement, and act deliberately there — not to avoid reasoning about performance until a problem is already reported. A performance issue investigated without a methodology degenerates into "guessing where the problem may be and then changing things until it goes away" (Brendan Gregg, "Thinking Methodically about Performance," ACM Queue, 2013); a structured method that reasons from utilization, saturation, and error signals toward the actual bottleneck should be preferred over guess-and-check.

Recomputing a value from expensive I/O — a file parse, an external call, a large query — on every read, when the underlying source changes far less often than it is read, is a specific, recurring instance of this discipline: state the expected read frequency versus source-change frequency before deciding whether to cache, and treat a data path that is read much more often than its source changes as a caching candidate by default, not an exception to justify only after the cost is observed to be a problem.
