title: brittle-forgettable-defaults
trigger: when designing a mechanism whose correct behavior depends on each new case, caller, or endpoint being individually remembered to opt in or out

A mechanism whose correctness depends on every individual case being separately remembered — a new caller, endpoint, field, or code path each requiring someone to notice it and opt it in or out by hand — degrades over time through ordinary maintenance inertia, not through a bug. Each omission produces no error, no crash, and no test failure to surface it, so gaps accumulate silently even when every individual change was locally reasonable. This is a general defect of mechanism design, not only a security concern: any behavior that should apply uniformly but is implemented as a per-case exception list is brittle in the same way.

Example: an HTTP client library that logs full request URLs by default, with sensitive query parameters redacted only for endpoints someone has explicitly flagged. A new endpoint that happens to carry a session token or search query in its GET parameters is exposed in logs until someone notices and adds it to the redaction list — there is no mechanism forcing that discovery, only the hope that whoever adds the endpoint also remembers, is aware of, or thinks to search for the redaction convention.

Prefer a mechanism where the safe/correct behavior is structural — derived from a property every case already has (a type, a naming convention, a schema annotation) — over one requiring a maintained list of exceptions: a positive/inclusion-based design (apply the treatment to everything, explicitly exempt the few cases that don't need it) fails closed when someone forgets to update it, while a negative/exclusion-based design (apply the treatment only to explicitly flagged cases) fails open. When an exclusion list is unavoidable because the full set of cases can't be enumerated or annotated structurally in advance, add an automated check — a test asserting the default behavior, a lint rule, a required review step triggered by the kind of change that should extend the list — that makes forgetting to extend it fail loudly. The failure mode has no other cheap detection point: nothing else about the system signals that a gap now exists.
