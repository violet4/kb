title: fail-open-defaults-and-secure-by-exception
trigger: when designing an access-control, permission, or filtering mechanism that must remain safe as new cases are added over time

A security control must be secure-by-default, not secure-by-exception: the safe state must be what happens automatically when nothing has been configured, not a special case that must be actively carved out and separately maintained for each new addition. A default-allow (fail-open) control — an allowlist that admits anything not explicitly excluded, a filter that passes through anything not explicitly caught — degrades not through a bug but through ordinary maintenance inertia: each new case that should have been added to the safe list is an omission with no error, no crash, and no test failure to surface it, so the gap accumulates silently over time even when every individual change was reasonable in isolation.

Prefer a positive security model (deny by default, explicitly allow only what is known-good) over a negative security model (allow by default, explicitly deny only what is known-bad) wherever the full set of safe cases can be enumerated: a positive model fails closed when someone forgets to update it, a negative model fails open. When a negative model is unavoidable (the safe set cannot be fully enumerated in advance), treat every new addition to the denylist as a security-relevant change requiring the same review rigor as the original design, and add an automated check (a test asserting the default state, a lint rule, a required review label) that makes forgetting to extend the exclusion list fail loudly rather than silently — the failure mode has no other cheap detection point, since nothing else about the system signals that a gap now exists.
