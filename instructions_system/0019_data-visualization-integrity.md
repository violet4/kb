title: data-visualization-integrity
trigger: whenever producing, reviewing, or modifying any chart, graph, or visual encoding of numeric data (histogram, bar/line/scatter plot, heatmap, or similar) -- in code, a notebook, a slide, or any other medium, independent of whether the surrounding activity is itself an engineering task

A chart's visual encoding must be truthful: the perceived magnitude of a mark (bar length, bar area, point position, color intensity) must be directly proportional to the data value it represents, with no second, unstated transformation stacked on top. Before treating a chart as finished, verify this explicitly — rendering without error and "looking like a chart of this type usually looks" is not evidence of truthfulness; check that the encoding geometry is actually honest, the same way a schema change needs explicit verification, not just an assumption that "it ran without error" was sufficient (see [[data-representation-and-schema-design]]).

This is Tufte's Graphical Integrity principle (Edward Tufte, *The Visual Display of Quantitative Information*): the representation of numbers should be directly proportional to the quantities represented. Tufte's Lie Factor formalizes this as (effect size shown in the graphic) / (effect size in the underlying data); a truthful graphic has a Lie Factor near 1.0, and anything outside roughly 0.95–1.05 is a measurable distortion, not a style choice. Common violations: truncated/non-zero axis baselines that exaggerate differences, 3D effects applied to 2D data, inconsistent interval spacing presented as a continuous scale, and area/volume used to encode a linear quantity (area grows with the square of linear size, so this silently exaggerates every ratio).

For histograms specifically, apply the Area Principle: the AREA of each bar, not just its height, must be proportional to the count or frequency it represents. This only reduces to "equal height means equal count" when every bucket has equal width. The moment bucket widths differ — including log-scale buckets chosen from a conventional tick sequence like 1-2-5-10-20-50 rather than genuinely equal width — equal-width bars drawn across unequal-width buckets break the area-proportional relationship, even if each bar's height alone is correct for its own bucket. There are exactly two honest options for unequal-width bins: size each bar's width to its actual bucket width (so area stays proportional to count), or keep bars equal-width and switch the y-axis to frequency density (count / bucket width) rather than raw count. A log-scale axis is not an exception to this — it is still a continuous number line, and bucket edges must be evenly spaced in log-space (not in a human-friendy 1-2-5 sequence) for equal pixel-width bars to be honest.

Never apply more than one transform to the same encoding dimension. A log-scale x-axis combined with a log-scale y-axis height on top of unequal bucket widths compounds three separate distortions into one chart, and each one individually defeats the reader's ability to recover the real distribution by eye — this is strictly worse than any single distortion alone, because the errors are not visually distinguishable from each other or from a correctly-encoded chart. When a long-tailed distribution's small values are hard to see on a linear axis, the correct fix is a log-scale axis on that one dimension only (with evenly-spaced-in-log buckets, per above) or a cumulative/rank-based view (e.g. "count of values ≥ X" as a function of X) — not a second compression stacked on the first to force more visual range out of the same chart.

A chart intended for a STEM/technical audience must survive the question "what number does this mark actually represent, and can the reader recover that number by looking at the mark alone, without reading a caption that explains away a distortion?" A caption or axis label describing an unusual scale does not repair a dishonest encoding — Tufte's labeling principle (clear, detailed, thorough labeling defeats graphical distortion) applies to legitimate complexity like log scales or annotated outliers, not to papering over a geometry that misrepresents the data. If the chart requires a disclaimer to not mislead, the chart is wrong; fix the encoding, don't caption around it.
